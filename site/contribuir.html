01 — Por que contribuir

Uma ferramenta de cinema que ninguém pode fechar

Documentário e cinema independente vivem de acervos enormes, orçamento curto e material sensível. O Talho existe para esse mundo — e, por ser livre, continua existindo mesmo que o mercado de assinaturas mude de ideia.

  • Livre de verdade, para sempre

    Com a GPL-3.0, ninguém pode pegar o código, trancar e alugar de volta. Toda versão distribuída continua aberta — inclusive as que ainda nem existem.

  • Pensada a partir da sala de montagem

    As regras vêm de quem edita: medir antes de sugerir, nunca cortar silêncio automaticamente, nunca tocar no arquivo original. Quem monta sabe o que falta — e aqui pode construir.

  • Um projeto de verdade, aberto por inteiro

    Cerca de 49 mil linhas de Python e 89 mil de JavaScript, testes automatizados e planos que registram o que deu certo e o que deu errado. Dá para aprender lendo — e ensinar contribuindo.

As quatro liberdades do software livre, garantidas pela GPL-3.0

  1. 0

    Usar

    Para qualquer finalidade: o seu filme, o acervo da instituição, a aula, o trabalho pago. Sem conta e sem assinatura.

  2. 1

    Estudar

    Todo o código está aberto. Dá para ler como a busca, a timeline e o render funcionam — e adaptar ao seu jeito.

  3. 2

    Redistribuir

    Copie e passe adiante: para a turma, a produtora, o coletivo, o festival.

  4. 3

    Melhorar e compartilhar

    Modifique e distribua a sua versão — desde que ela continue livre, sob a mesma GPL-3.0.

As liberdades contam a partir do zero, como todo bom índice.

03 — Roadmap

Onde o Talho está — e para onde vai

Sem datas e sem promessas: um projeto em construção avança no ritmo de quem constrói. A agulha marca onde estamos agora.

  • Concluída
  • Em andamento
  • Planejada

Quer saber o que vem antes do quê? A ordem de implementação, conferida contra o código, organiza os próximos passos em ondas — de “destravar” e “sanear” até “cena e filme”. Os documentos às vezes ficam atrás do código; ajudar a mantê-los fiéis também é contribuição.

  1. Concluída

    Etapa 1 — Sanear a base

    Limpeza do pipeline de análise: a fundação sobre a qual todo o resto foi construído.

  2. Concluída

    Etapa 2 — Segmentação e CLIP local

    Suíte NLE Clássico — Tasks 0 a 15

    Layout em duas zonas, ferramentas Lâmina, Slip, Slide e Rolling, montagem de 3 e 4 pontos, Match Frame, Replace Edit, subclipes, timecode, freeze frame, velocidade, Rate Stretch e crossfade de áudio.

  5. Em andamento

    Transições, camada de ajuste, cor sólida e os recursos de áudio e organização que faltam na timeline.

04 — Primeiro PR

Seu primeiro Pull Request em cinco passos

Pull Request (PR) é o pedido para juntar a sua mudança ao projeto. Parece cerimônia, mas é só isto: copiar, mexer num ramo seu, registrar, enviar e pedir revisão.

  1. Passo 1

    Fork: a sua cópia

    No GitHub, clique em Fork no topo do repositório. Você ganha uma cópia na sua conta, onde pode mexer à vontade. Depois, traga essa cópia para a sua máquina:

    Terminal 
    git clone https://github.com/SEU-USUARIO/capiau-talho-v03.git
cd capiau-talho-v03
# o repositório original, para buscar novidades depois
git remote add upstream https://github.com/fernangcortes/capiau-talho-v03.git

  2. Passo 2

    Branch: um ramo por assunto

    Nunca trabalhe direto na main. Abra um ramo com nome que diga o quê: feature/… para recurso, fix/… para correção, docs/… para documentação.

    Terminal 
    git checkout -b feature/minha-melhoria

  3. Passo 3

    Commit: registre o que mudou

    Confira o que mudou, adicione só os arquivos da mudança e escreva a mensagem no padrão da casa (veja ao lado). O .env com as suas chaves nunca entra — o .gitignore já o ignora, mas confira.

    Terminal 
    git status
git add caminho/do/arquivo
git commit -m "docs(wiki): esclarece um passo da instalação"

  4. Passo 4

    Push: envie para o seu fork

    O ramo sobe para a sua cópia no GitHub. Nada muda no projeto original até alguém revisar e aceitar.

    Terminal 
    git push origin feature/minha-melhoria

  5. Passo 5

    Pull Request: peça para juntar

    No GitHub, abra o Pull Request do seu ramo para a main do projeto. Conte o que mudou e quais testes você rodou — isso acelera a revisão. Um roteiro para a descrição:

    Descrição do PR 
    ## O que mudou
- …
## Por quê
- …
## Testes que rodei
- python -m pytest tests/ -v
- node tests/autoteste_match_frame.mjs

Convenção de commits

tipo(escopo): descrição

É o estilo real do histórico: o tipo, a área entre parênteses e uma descrição curta, em português e em minúsculas.

feat
recurso novo
fix
correção
docs
documentação
perf
desempenho
test
testes

Exemplos tirados do histórico

  • feat(ui): gerador de cor sólida isolado na biblioteca e transições de junção na timeline
  • fix(player): corrigir geometria de caixas faciais e descarte no Source Player
  • docs(ordem): aplicar a revisão adversarial da ordem de implementação
  • test(nle): autotestes de transições de vídeo, camada de ajuste e render cache

Monte a sua mensagem

Tipo
Seu commit 
git commit -m "feat(timeline): o que mudou, em poucas palavras"

05 — Ambiente

Prepare o ambiente em poucos minutos

Backend em Python na sua máquina, interface no navegador, em http://localhost:8000. Não precisa de GPU.

Antes de tudo

  • Gito pip também usa: uma dependência vem direto de um repositório
  • Python 3.12o recomendado (3.10 ou mais novo é compatível)
  • FFmpego ffmpeg e o ffprobe, os dois no PATH
  • Node.jspara os autotestes da timeline e da interface

Segurança: a API não tem autenticação — use só na sua máquina (no Docker, publique em 127.0.0.1:8000:8000). E nunca faça commit do .env.

Sobre o --reload: no Windows, rodando sem console, o recarregamento já derrubou o servidor em vez de reiniciá-lo. Se acontecer, rode sem ele e reinicie a cada mudança no backend.

Prefere Docker? docker compose up --build sobe tudo, e o código em src/ recarrega ao ser editado. Instalação passo a passo.

bash 
# 1. ambiente virtual com Python 3.12
python3.12 -m venv .venv
source .venv/bin/activate
# 2. dependências
pip install -r requirements.txt
# 3. configuração: preencha só as chaves que for usar
cp .env.example .env
# 4. servidor com recarga automática
uvicorn src.api.server:app --reload
PowerShell 
# 1. ambiente virtual com Python 3.12 (ou: uv venv .venv --python 3.12)
py -3.12 -m venv .venv
# 2. dependências (ou: uv pip install -r requirements.txt)
.venv\Scripts\pip install -r requirements.txt
# 3. configuração: preencha só as chaves que for usar
Copy-Item .env.example .env
# 4. servidor com recarga automática
.venv\Scripts\python -m uvicorn src.api.server:app --reload

Depois, abra http://localhost:8000 no navegador.

06 — Testes

Rode os testes antes do PR

Duas baterias: pytest para o backend e autotestes em Node para a timeline e a interface. Rode as que tocam no que você mudou — e conte no PR quais foram.

78

arquivos Python em tests/ — a bateria do pytest

83

arquivos .mjs — os autotestes em Node, quase todos autoteste_*.mjs

Backend · pytest 
# na raiz do projeto, com o .venv ativo
pip install pytest
python -m pytest tests/ -v
# só um arquivo
python -m pytest tests/test_f11_export.py -v
Interface · Node 
# um autoteste específico
node tests/autoteste_match_frame.mjs
# todos, em sequência (Linux e macOS)
for f in tests/autoteste_*.mjs; do node "$f" || break; done

No Windows, o README traz um comando de uma linha, em Node, que roda todas as baterias em qualquer sistema.

Cuidado com o seu acervo: hoje, parte dos testes ainda abre o banco real em data/ — trocar isso por um banco temporário está na lista de consertos da ordem de implementação. Rode a suíte com o servidor fechado e, se houver um acervo de verdade ali, faça backup antes. (Aliás: esse conserto daria um belo PR.)

docs · ordem de implementação

Lições que viraram regra

Log não pode mudar o pipeline

Uma seta num log não cabia no console do Windows; o erro era engolido por um try amplo e a análise voltava, em silêncio, para o relógio fixo de 10 s. Hoje: log simples e fora do try.

Teste com o tipo real, não com um dublê

Os testes de rajadas de fotos passavam usando um dicionário no lugar da classe de configuração — e o código quebrava de verdade. Hoje os testes usam a classe real.

Valide no programa que vai abrir o arquivo

Um .otio correto pelo padrão não abria no Kdenlive. Só o teste no programa real mostrou o problema — e mudou o jeito de gravar o caminho da mídia.
